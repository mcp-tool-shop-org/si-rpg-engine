## Q1 — Where do the two poses live?
ANSWER: In the host, as the last two frames it was handed, and nowhere on `Frame`. The frame already carries the only sequence number a blend needs: `tick`, with `DT` fixed, so simulation time is `tick * DT` and no timestamp field is missing. The blend may read, per body matched by `id` across the pair, `x` and `y`; it may read `vx` and `vy` only to detect a discontinuity, since a change in position larger than velocity times `DT` is a spawn or a teleport, and the host snaps instead of sliding. That is derived from committed fields, not a new flag. A body present in one frame and not the other is drawn at its committed pose with no blend. On the first frame there is no pair, and the host draws it as committed. The host's memory is presentation: it dies with the process, replay never reads it, and nothing in it can reach the hash because the hash was taken before `draw` was called.
CHANGE IN THE SLICE: "the host may blend two committed poses" becomes "the host blends the last two frames it received, matched by body id; a position change larger than velocity times DT is drawn as a cut."
CONFIDENCE: high
BASIS: `types.d.ts` and `frame.js` on main; the Fiedler page for delayed interpolation

## Q2 — May draw block the quantum?
ANSWER: No, and today it can, so this is the first tick change. `draw` stays synchronous, because a callback is the simplest boundary Atlas can see, but two things change. The tick wraps the call: a host that throws is detached and the quantum completes; a host that blocks is a defect the tick cannot see, so the host's contract is that `draw` does nothing but push the frozen reference into a two-slot ring and return. The presentation loop, on a timer, reads the ring and draws at real time. That is where the burst problem lands: an admitted move of 256 quanta arrives in one synchronous call, four seconds of simulation in microseconds, and a two-slot ring keeps only the last pair, so the picture would show the end of every action and none of the motion. A ring cannot fix that, because the burst is the tick's cadence, not the host's. The fix is a quantum pump: `submit` declares and admits and schedules the action's quanta, and a separate `advance()` runs one quantum. `play`, `replay`, and the tests call `advance` until idle, and the hash sequence is unchanged for the same log. The host slice then paces the law at one `advance` per `DT` of real time, and the tick still runs without drawing. A dropped frame loses nothing but a pose the person did not see; the hash cannot change because every frame was hashed and frozen before any host saw it.
CHANGE IN THE SLICE: add "the tick guards `draw`; the tick exposes `advance()`, and `submit` no longer runs an action's quanta itself."
CONFIDENCE: high on the guard; high on the pump being necessary; medium that it is as small as I think
BASIS: `tick.js` lines 62–64 and 100–103 on main

## Q3 — What is the first picture?
ANSWER: An in-repo page that draws the hashed boxes on a canvas, fed by a Node process that runs the tick, because the tick cannot run in the page: `predicates.js` imports `node:fs`. That is the honest reason the first host is two processes, not a preference for clients. The Node side is `play` grown one door: it runs the tick, pumps quanta at real time, and writes each committed frame as one JSON line to a local socket. The page reads the stream, keeps two frames, blends, and draws rectangles at `hw` and `hh`. No client engine. If one is ever named, the rule is that it instantiates no physics body: bodies are sprites placed at blended poses, and its collision layer does not exist. A screenshot of the walker falling to the floor between two walls is the slice's proof of plumbing. I refuse to call it a scene. A scene has something worth wanting, which is the same bar the frozen seat is waiting on, and this slice does not add one.
CHANGE IN THE SLICE: "a scene a person has looked at" becomes "a picture a person has looked at; the scene arrives with the first content."
CONFIDENCE: high on two processes; medium on the socket over a simpler pipe
BASIS: `predicates.js` on main imports `node:fs`

## Q4 — Where does a person's intent enter?
ANSWER: In the Node process, beside the pump, not in the page. The page sends a key or a click as a request naming the body id it hit, found by testing the pointer against the boxes of the frame it is displaying, which is reading committed fields, not casting a ray in a second world. The adapter in the Node process turns that into an `Intent` with the hash of the newest committed frame it holds, and calls `submit`. Not the displayed frame's hash: the picture lags by design, and an intent stamped with the displayed hash would be refused whenever the tick had advanced. With one host in one process the newest frame is the tick's current frame whenever the tick is idle, and while an action is pumping the adapter queues the request for the next boundary. The adapter holds `submit` and frozen frames and nothing else, so it cannot write `x` or `vx`. The stale check keeps its meaning across hosts, not within one.
CHANGE IN THE SLICE: add "the adapter stamps the newest committed hash it holds, and queues input until the action boundary."
CONFIDENCE: high
BASIS: the stale-frame check in `tick.js` and the host-boundary test

## Q5 — What falsifies the slice?
ANSWER: The assumption that a person can act on what they see. Today an action resolves in one synchronous burst, so a person could only ever submit between actions, and the picture would replay motion that is already over. If that is acceptable for the first picture, the slice is a canvas and a stream. If a person must be able to act mid-motion, which any game needs, the pump in Q2 is not a refinement of this slice, it is the slice, and the canvas is its proof. What I would write instead: the pump first, as a tick change with the existing nine tests unchanged in outcome and the golden untouched, then the two-process host on top of it. One paragraph of PHASE-0 records that resolve now happens across `advance` calls rather than inside `submit`, which is what the plan already says it does.
CHANGE IN THE SLICE: the host slice is gated on the quantum pump.
CONFIDENCE: high
BASIS: `tick.js` lines 100–103; the plan's own sentence that an action resolves across quanta

SCAR: Gemini's scar wants presentation colliders for particles and hover. Particles that bounce off a box for pixels are fine, and hover is reading the frame's boxes. The line is narrower than "no second collider" and harder than Gemini's: a computation whose result becomes any field of an intent may read only committed frame fields. A ray cast against anything else to choose a target is a second world the moment its answer is submitted. And against the brief: the picture cannot be the next thing written while `submit` runs the whole action, because there is nothing to watch, only something to replay.
